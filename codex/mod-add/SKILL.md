# 添加子代理

先识别实际运行的 CLI，不按当前模型名推断。若在 Grok CLI 中加载本文件，改读本文件真实路径对应的 [Grok 版](../../mod-add/SKILL.md)，或已安装的 `~/.grok/skills/mod-add/SKILL.md`；确认目标不是本文件后，按该版执行。找不到对应版本时提示安装，不执行下面的 Codex 流程。

与同级的 `mod-dispatch` 一起安装。使用 [relay.py](../mod-dispatch/scripts/relay.py) 管理连接；把文中的 `<relay.py>` 替换为该脚本的实际绝对路径。需要 macOS/Linux 和 Python 3.9+，无第三方依赖。

本套调度通过 HTTP Chat Completions 调用第三方模型。它不会把模型注册进 Codex 原生 `/model` 或内置子代理列表，也不修改 `~/.codex/config.toml`。

## 自动生成连接文件

用户要求配置或添加模型即已授权本地配置操作，无须重复询问。先运行：

```sh
python3 -B <relay.py> init
```

脚本自动在整套技能包主目录生成 `connection.json`，输出其实际路径；已有文件保留。直接使用本源码包时为 `mod-agent-skills/connection.json`；按 README 分别复制两个技能安装后为 `~/.agents/skills/connection.json`（项目安装时为 `.agents/skills/connection.json`）。不放在 `mod-add` 子目录中。文件权限为 `0600`，`--config <绝对路径>` 可指定其他位置。

已有 JSON 若仅因地址缺少协议而被 `init` 拒绝，保留文件，按后面的端点识别流程修正；不要把可修正的地址格式误报成必须由用户重填。

旧 Grok 连接可能只有地址和密钥。若原 JSON 仅缺 `models` 或其中某些角色，由代理先解析原文件，按下方默认映射仅补缺失的角色，保留所有已有字段和模型值，以 JSON 序列化写回并设为 `0600`，再继续端点识别和 `/models` 验证。此迁移不能直接使用 `configure`，因为脚本会先校验旧文件；如果 `models` 存在但不是对象、已有角色值类型错误或其他字段无效，报告问题并保留文件，不重建覆盖。

首次需要用户填写时，主动打开连接文件所在目录供用户编辑（macOS 使用 `open <目录绝对路径>`），同时给出文件链接。用户保存后再读取，不在编辑期间覆盖文件。若当前运行环境无法打开目录，说明实际错误并提供路径，不声称已经弹出。

默认内容：

```json
{
  "base_url": "",
  "api_key": "",
  "models": {
    "read": "deepseek-flash",
    "write": "deepseek-v4-pro",
    "brain": "gpt-6-luna",
    "review": "grok-4.7"
  }
}
```

这些 ID 是沿用 Grok 版的初始映射，不代表中转站一定提供这些模型。使用服务实际返回的完整 ID。

## 填写与更新

- 用户可以编辑生成的文件，也可以在对话中提供地址和密钥，由代理代填。没有连接信息时，先生成文件再提示缺少的字段；不要让用户自己建文件。
- 把待更新字段组成 JSON，通过标准输入交给 `python3 -B <relay.py> configure`。仅更新给出的字段，`models` 按角色合并。使用进程标准输入或正确转义的内存管道，避免 shell 展开；不要将真实密钥写进命令行参数、技能正文或仓库，也不在回复中复述。
- `base_url` 接受域名入口、API 基础路径或完整端点，例如 `relay.example`、`https://relay.example/v1/`、`https://relay.example/v1/chat/completions`。由代理按下一节识别并保存规范地址，不让用户手动补 `/v1` 或删端点。不能使用含账号、查询参数或片段的 URL。
- 用户要求复用 Grok 连接时，从 `~/.grok/skills/connection.json` 读取同一组 `base_url`、`api_key`，通过 `configure` 写入；旧版文件可能位于 `~/.grok/skills/mod-add/connection.json`，仅在新路径不存在时检查旧路径。直接使用本源码包时两版共享包主目录的连接文件，不需要复制，不覆盖 Codex 的角色映射。
- 更新已配置的地址时，同时提供该服务对应的密钥。同一 origin（协议、主机、端口）内规范化路径时，将当前密钥与规范地址一并传给 `configure`；更换服务时需要用户提供配套密钥或明确要求沿用，不自动把旧密钥发往新服务。
- 文件无法解析或连接不完整时保留原文件，说明需要修复的内容；不发送模型请求。

## 自动识别端点与运行环境

1. 先辨认当前 CLI。本版在 Codex 中通过 `relay.py` 外部调度，脚本直接用 `base_url + /models` 或 `base_url + /chat/completions`，不会自动添加 `/v1`。基础路径取决于服务实际路由和客户端拼接规则，不是“Codex 固定加 `/v1`、Grok 固定不加”。不把 Grok 的 `api_backend` 或模型表复制进 Codex 配置。
2. 在内存中整理候选地址：无协议的域名入口先在用户指定的同一主机上补 HTTPS，不擅自降级 HTTP；去掉尾斜杠，识别并去掉末尾 `/models`、`/chat/completions` 或 `/responses`，保留前面的 `/v1`、`/api/...` 等自定义路径。完整端点只能提供协议线索，不能证明服务支持该协议。
3. 使用用户提供的同一连接和密钥做少量真实请求，先检查候选基础地址下的 `GET /models`。裸域名入口的 `/models` 返回 404 时，再检查 `/v1/models`；已有自定义路径不随意裁掉或枚举。最多核对 3 个有依据的候选；401、403、429 应按认证、权限或限流处理，不能当作路径错误换地址重试。不得跨 origin 发送密钥或跟随重定向转发密钥。
4. 使用内存中的连接副本组织请求，不为探测写临时配置，也不反复改真实连接文件。确认模型列表响应有效后，用 `configure` 保存规范 `base_url`。若原文件地址缺少协议，脚本会先拒绝读取旧配置；此时由代理解析原 JSON，验证补 HTTPS 后的候选，再通过 JSON 序列化仅更新 `base_url`、保留其余字段并设为 `0600`。脚本没有自动发现端点的命令，这些判断由代理完成。若服务没有模型列表，根据用户提供的信息或服务文档判断，保留未验证状态，不声称已连通。
5. 列表成功不证明推理协议兼容。用户要求实际测试时，只对一个已选模型发一条简短请求，不自动付费轮测所有模型。若确认服务只支持 Responses，明确报告当前 helper 不兼容；不能仅改 URL 就声称已适配。给出所需的协议适配方案，再按用户授权范围处理。

## 验证与交付

```sh
python3 -B <relay.py> models
```

端点识别后，此命令使用规范连接请求 `/models`，列出 ID 并核对四个角色的映射。若刚完成同一次有效列表请求，可直接核对其结果，不必重复请求。若角色缺失，让用户选择该角色实际可用的模型，再用 `configure` 更新；不要猜别名或悄悄换模型。若服务不提供 `/models`，如实报告，依据用户提供的模型 ID 配置，实际调用成功前标记为未验证。

列出模型成功只证明认证、列表和 ID 匹配，不证明文本或工具能力。用户要求测试时，使用 `ask --role read --workspace <项目绝对路径>` 发送一条简短任务作实际验证；外部推理会使用用户中转站的额度。

最后报告连接文件路径、规范地址、当前 CLI 的调用方式、四个角色的模型 ID、验证结果和下一步缺失信息。之后通过 `$mod-dispatch` 调度，不需要切换 Codex 主模型。
